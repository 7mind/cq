# T679 — Re-measuring the shipped ledger MCP response contract against the RS3 corpus

Task: `tasks:T679` (goal `goals:G93`, validates `researches:RS3`).
Date: 2026-07-25. Harness: `docs/drafts/20260725-2130-t679-rs3-remeasure/`.

## 0. What kind of number each figure is

Three different quantities appear below. They are never mixed, and none of them
is a billing figure.

| Label used below | Meaning |
|---|---|
| **measured wire shape** | UTF-8 bytes and `o200k_base` tokens of one serialized MCP request or response, produced by the code under measurement. |
| **RS3 simulated bound** | RS3's own hand-modelled "what a compact/ack contract could remove" number. RS3 called it an upper bound; it is quoted here only for direction, never as a realized result. |
| **scenario** | An arithmetic combination of measured quantities under an explicitly stated assumption (e.g. "the tool schema is paid once per subagent context"). A scenario is a conditional, not an observation. |

**No claim in this report converts any of the above into realized billing
reduction.** Realized cost depends on call mix, prompt/tool-schema caching, host
framing, and reasoning length — none of which this probe observes. `o200k_base`
is a reproducible accounting proxy, not the tokenizer Anthropic models bill
with; RS3 used the same proxy, which is what makes the two comparable.

## 2. Method

RS3 simulated the "after" side. This task does not: for every captured tool
result, the after-shape is computed by passing the captured payload through the
functions the shipped server actually calls —
`projectItemDto`, `projectMilestoneItemGroupsDto`, `projectFtsSearchResultsDto`,
`projectFetchedMilestoneDto`, `projectItemMutationAckDto`,
`projectMilestoneMutationAckDto`, `projectLedgerMutationAckDto` from
`packages/ledger/src/mcp/wireResponseContract.ts` — inside the same envelopes
those handlers build (`{item: …}`, `{items: …}`, `{results: …}`,
`{milestone: …}`, `{ledger: {id}}`) and serialized as the same minified JSON.

Where the corpus is silent (five cutover-affected tools have zero captured
calls), §6 measures the real RS3-era server and the real current server side by
side on an identical operation script instead of modelling them.

Exact commands: `docs/drafts/20260725-2130-t679-rs3-remeasure/README.md`.

### Corpus walk: MCP server namespaces

Host tool names are `mcp__<server>__<tool>`, and the ledger server appears under
**two** namespaces in this corpus: `ledger` (710 calls) and the plugin-provided
`plugin_claude-code-home-manager_ledger` (5 `fetch_item` calls). The server
segment therefore contains underscores, and a pattern restricting it to
`[A-Za-z0-9-]` drops the plugin namespace entirely. An earlier revision of
`remeasure.ts` did exactly that and silently under-counted by 5 calls
(710/366 rather than 715/371) — which is also why it did *not* reproduce RS3's
inventory. The probe now splits the server segment non-greedily at the first
`__`, and, so that this class of error cannot recur silently, records a
`mcpToolNameAudit` in the artifact — ledger calls broken down **by server
namespace**, the ignored non-ledger tool names, and a counter of `mcp__*` names
that fail to split at all, which is an assertion failure (exit 1) if non-zero.

### The 8 unreplayable calls, and the one-directional gap they leave

All 8 are calls whose payload the **host elided** before it reached the
transcript, replacing it with a pointer notice. Two distinct host mechanisms,
both self-describing:

| Tool | Calls | Notice form | Stated elided size |
|---|---:|---|---|
| `fetch_ledger` | 6 | `Error: result (N characters …) exceeds maximum allowed tokens` | 140,080 ×3, 278,842, 131,669, 148,025 = **978,776 characters** |
| `fts_search` | 2 | `<persisted-output> Output too large (N KB)` | 53.8 KB + 52.3 KB = **106.1 KB** |

The saved-payload files the notices point at no longer exist, so these calls
cannot be replayed — the same blind spot RS3 recorded ("every `fetch_ledger`
result overflowed"). But the notices state what they replaced, so the gap can be
*bounded* rather than merely named. Taking the host's `KB` as decimal or binary
gives **1,084,876–1,087,422 bytes**; at this corpus's own measured ratio of
**3.8064 bytes/token** that is **285,015–285,684 tokens ≈ 44% of the 645,670
before-tokens actually measured**. In other words **only ~69.3% of the true
before-volume was measured** (`unmeasuredBeforeVolume` in the artifact).

**This bias is one-directional, and it runs in the contract's favour.**
`fetch_ledger` is a mandatory-projection tool; all six captured calls omitted
both `compact` and pagination, used the RS3-era default-full path, and
overflowed *because* the payload was large — as did the two `fts_search`
results. Every compact projection is a key-subset of the full entity, so no
replayed call can save a negative amount; replaying these 8 could therefore only
have **increased the absolute saving**, and only moved every §8 scenario further
toward saving. Two things follow, and they differ in strength:

* the **−480,119-token absolute figure and all three §8 scenario rows are strict
  lower bounds on the saving** (upper bounds on the cost);
* the **74.36% figure is a rate over the replayed subset, so it is not itself a
  bound on the true corpus-wide rate — but the true rate *is* bounded, to
  [51.55%, 82.22%]**. The compression ratio of the 8 elided payloads is
  unobservable; unobservable is not the same as unbounded. Write *S* for the
  saving those calls would have contributed and *B* for their before-volume.
  The two facts just established pin *S* to `[0, B]`: `S ≥ 0` because every
  compact projection and acknowledgement is a key-subset of what the RS3-era
  server returned, and `S ≤ B` because no after-shape is negative. With
  measured *M* = 645,670 before-tokens, measured saving 480,119 and
  *B* = 285,015–285,684, the true rate `(480,119 + S)/(M + B)` spans
  `480,119/(M+B)` to `(480,119 + B)/(M+B)`. The first is decreasing in *B* and
  the second increasing in *B*, so the widest admissible interval is at the
  largest *B*: **480,119/931,354 = 51.55%** to **765,803/931,354 = 82.22%**.
  The harness derives this from the same three measured quantities
  (`corpusWideSavingRateBounds` in the artifact, min/max over both *B*
  endpoints); it is not typed in.

Note the exclusion is recorded for the right reason. `remeasure.ts` carries a
real `fetch_ledger` replay transform (both the paginated and whole-ledger
envelopes, via the shipped `projectPaginatedLedgerDto` /
`projectFetchedLedgerDto`), so the artifact's recorded reason for all six is
`host oversize/error notice, payload not captured` — an elided payload, not a
missing transform.

that is shown the tool list**, plus **4 tokens per projection-bearing call**.

## 5. Full-content control

Compact-only measurement would flatter the result, because `projection:"full"`
still exists and is used deliberately. Two controls:

1. **Corpus control.** For all 558 replayed projection-tool calls the probe also
   computed the `projection:"full"` response and compared it to the captured
   payload: `fullControlDeltaTokens = 0` for every tool, and a canonicalized
   deep-equality assertion (`full === captured payload`) passed on every call.
   The full path returns exactly what the RS3-era server returned — it saves
   nothing and loses nothing, and it now costs +4 input tokens per call.
2. **Requested-full-content class.** `read_log`, `fetch_prompt`,
   `fetch_ledger_archive`, `get_config` are declared `requested-full-content` /
   `purpose-built-small` in `LEDGER_RESPONSE_CONTRACTS`, and the corpus confirms
   byte-identical volume for those of them that appear with a non-error result
   (`get_config` and `fetch_ledger_archive`: 1,833 tokens over 7 calls,
   unchanged).

A useful consequence for call-mix reasoning: if a fraction *f* of today's
projection-bearing calls must use `"full"`, the response saving scales by
(1 − *f*) while the +4/call input cost is paid regardless. At *f* = 1 the
contract is a pure request-side cost. **This is a scenario, not a measurement of
how callers actually split** — the corpus predates the contract and therefore
contains no evidence about the future full/compact mix.

## 8. Net accounting, and what it does not say

Measured, on this corpus:

* response side: **−480,119** tokens (−1,953,295 bytes) over 693 calls;
* per-call request side: **+2,316** tokens over 579 projection-bearing calls;
* cold schema: **+2,214** tokens attributable to the contract, once per context
  that receives the tool list (+2,498 measured total growth between the two
  commits, of which 284 is unrelated).

The first two are directly comparable — same calls, same corpus — and net to
**−477,803 tokens**. The third is per-context, not per-call, so combining it
requires an assumption about how many contexts pay it. The corpus contains 357
transcripts, of which **200 make at least one ledger call**:

| Scenario (assumption stated) | Corpus-wide net |
|---|---:|
| Tool schema fully cached, or its cost ignored | **−477,803 tokens** (saving) |
| Schema charged once per transcript that calls the ledger (200) | **−35,003 tokens** (saving) |
| Schema charged once per transcript, called or not (357) | **+312,595 tokens** (cost) |

These are scenarios. Which one is closest to reality depends on prompt/tool
caching behaviour and on whether the ledger MCP server is attached to contexts
that never call it — neither of which this probe measures, and neither of which
should be guessed at here.

**All three rows are computed on ~69% of the true before-volume**, because the
host elided 285,015–285,684 tokens' worth of payload from 8 calls before they
reached the transcript (§3). That omission is **one-directional in the
contract's favour**: every elided call is a large mandatory-projection response
that overflowed on the RS3-era default-full path, so replaying it could only
enlarge the saving. Each row above is therefore a **lower bound on the saving**
(equivalently, an upper bound on the cost), and the third row's +312,595-token
cost is the *most* pessimistic reading available rather than a point estimate.
The magnitude is not negligible relative to the effect being measured: the
unmeasured before-volume is ~44% of the measured one. It is, however, bounded
in both directions rather than open-ended — the true corpus-wide saving rate
lies in [51.55%, 82.22%] (§3), so even the worst admissible case saves more than
half the response volume.

The distribution matters more than the aggregate: the **median** ledger-calling
transcript saves **1,461** response tokens, which is *less* than the 2,214-token
schema delta; only **76 of 200** calling transcripts save more than it. The
saving is concentrated in read-heavy orchestrator sessions (max observed:
15,211 tokens in one transcript). Break-even is about **4.9 median replayed
`fetch_item` calls** per context — 2,214 ÷ 455, where 455 is the **median of the
per-call savings** of the 365 replayed `fetch_item` calls (the median of
differences; the difference of the medians, 587 − 133 = 454, happens to be
almost the same here but is a different quantity and is not used).

Explicitly **not** claimed: that any of this reduces a bill by any percentage;
that RS3's 419,366-token simulated bound was realized (it was a bound, over a
different candidate set, and this report neither confirms nor uses it as an
outcome); that a token saved on the wire is a token saved in a model's context
after host framing; that the measured before-volume is the whole before-volume
(it is ~69% of it, with the remainder biased toward more saving, §3).

payloads leave the *rate* uncertain within [51.55%, 82.22%], and the whole of
that interval is material saving: the acceptance clause "the measured
high-volume methods retain material savings in the direction RS3 predicted"
holds at 51.55% exactly as it holds at 74.36%. It therefore survives the
measurement gap outright — it is not contingent on the gap being small, on the
elided payloads compressing well, or on any assumption the probe cannot test.
The only quantity the gap actually threatens is the §8 aggregate arithmetic, and
it threatens it in the direction of *more* saving.

### One item for plan review (not fixed here)

The response contract's **request side costs 2,214 cold tokens per context**,
which exceeds the median per-transcript response saving (1,461) on this corpus.
The contract is still clearly correct for read-heavy orchestrator sessions and
for narrative payloads, and no response shape regressed — so this is not a
proposal to revert anything.

**Stated against a symmetrically-bounded picture**, the finding survives but is
narrower than the bare numbers suggest, and the caveat must travel with it:

* the 1,461-token median is computed on the ~69% of the before-volume that the
  host did not elide, and the unmeasured 31% is one-directionally biased toward
  *more* saving (§3). Were the elided payloads recoverable the median could only
  rise, never fall — and by a computable, small amount. The 8 elided calls sit
  in only **5** of the 200 calling transcripts (the six `fetch_ledger` calls in
  **3**), at ranks **61, 160, 184, 192 and 196** by net saving. Four of the five
  are already *above* the median and so cannot move it however far they are
  lifted; only the rank-61 transcript sits below it. Lifting **all five
  arbitrarily** — an unbounded perturbation, the strongest admissible one —
  moves the median from 1,461 only to **1,485.5**, against a schema delta of
  2,214 (`sessionAmortization.medianRobustnessToElidedCalls` in the artifact).
  The ordering "median saving < 2,214" therefore cannot be overturned by any
  recovery of the elided payloads. The *aggregate* scenarios in §8 have no such
  protection, and all three shift toward saving;
* the schema cost is a genuine per-context charge that caching changes the
  *price* of, not the existence of — a cold subagent context that is shown the
  tool list pays it whether or not it calls the ledger, and 157 of 357
  transcripts never call the ledger at all;
* the corpus predates the contract, so it says nothing about the future
  compact/full call mix (§5), which moves the response side but not the schema
  side.

So: not a revert, and not a claim that the contract loses. It is a request for a
decision on two cheap follow-ups that would make the win robust rather than
distribution-dependent:

1. **Shorten the repeated schema prose.** `ITEM_PROJECTION_DESCRIPTION` (a
   ~40-word sentence) is emitted twice per projection tool — once as the
   parameter description and again inside the `Authoritative response:` block —
   across six tools. The `Authoritative response:` blocks alone measure 1,162
   tokens. Compressing these could plausibly return a four-figure token count to
   every context at zero behavioural cost; the exact figure needs measuring, not
   estimating.
2. **Decide whether `fetch_milestone` should carry the mandatory projection at
   all.** RS3 recommended leaving it alone; the measured outcome on this corpus
   is a wash (−640 response tokens, +104 input tokens, 11 of 19 calls
   break-even).

Both are measurable with the committed harness by re-running §4 and §3 after the
change.
